# Team 2C — Voice Assistants (desktop-control slice)

Method: read the actual implementation files (2–4 per repo), desktop/Windows control only.
Common boilerplate across repos 1–6 (reported once): `speech_recognition` (Google STT) + `pyttsx3` TTS, `pyautogui` for any real mouse/keyboard work. Only repo 7 breaks the pattern.

## Melissa-AI/Melissa-Core (499★, DEAD — last commit 2018-10-01, MIT, original)
- What it claims / what it is: Cross-platform "virtual assistant" (the famous Melissa). In reality a Python 2 chatbot brain with joke/weather/music actions — **it has essentially no Windows desktop control at all.**
- HOW IT ACTUALLY WORKS (inside): entry → `melissa/__main__.py` hotword loop → `melissa/brain.py:query(text)` → dispatch → (almost no OS calls).
  - Intent matching is the one genuinely interesting part: `brain.py:query()` tokenises the utterance into a temp SQLite `expression` table (`actions_db.py`), JOINs it against a persistent `words`/`word_groups`/`functions` DB, scores each candidate word-group (full-match required; in-order match gets ×1.5 `order_match_factor`), breaks ties by a per-function `priority` column, then dispatches dynamically: `getattr(actions_db.modules[module_name], function)(text)`. Adding a skill = adding rows + a module with a `WORDS` dict — data-driven routing, no if/elif chain.
  - "Control" actions are toys: `actions/lighting.py` shells out to `blink1-tool` (a USB blink(1) LED: `--white/--cyan/--off`); `actions/system_status.py` reads `psutil`/`platform.uname()` and speaks it; `actions/play_music.py:music_player()` builds a shell string and runs `os.system("mpg123 '<path>'")` / `afplay`. No app launching, no volume, no windows, no hotkeys anywhere in the repo.
- Clever mechanism: the **SQLite word-group intent engine** (`brain.py`) — scored, ordered, priority-tie-broken, DB-extensible dispatch. Everything else is demo-grade.
- Hidden weaknesses: Python 2 only (`print` statements, `dict.iteritems()`) — won't even import on modern Python. `play_music.py` interpolates a filename into an `os.system` string (shell injection via a crafted filename). Function-name strings built by string concatenation into SQL (`"WHERE function IN (" + function_str + ")"`). Music path/listing assumes `mpg123`/`play` binaries that don't exist on Windows, so the "cross-platform" claim fails exactly on Windows.
- Stealable for a stdlib-only Python Windows assistant? **Yes — the pattern, not the code:** a tiny SQLite (stdlib `sqlite3`) word-group scoring router with order bonus + priority tie-break is a clean, dependency-free intent matcher. The control code itself: nothing to steal.

## Shokr/JARVIS (79★, DEAD — last commit 2021-04-11, NO LICENSE file, original-but-trivial)
- What it claims / what it is: "Control Windows programs with your voice." In reality a single 103-line `main.py` that listens **once** and opens one of seven hardcoded programs.
- HOW IT ACTUALLY WORKS (inside): entry → module-level code (not even inside a function): `sr.Recognizer().listen()` + `recognize_google()` runs at import → `main.py:get_app(query)` → `dict.get(query.lower())` exact-match against `{'browser': 'C:\\Program Files\\Internet Explorer\\iexplore.exe', 'calculator': 'calc.exe', 'cmd': 'cmd.exe', 'notepad': 'Notepad.exe', 'paint': 'mspaint.exe', 'shell': 'powershell.exe', 'stikynot': 'StikyNot.exe'}` → `subprocess.call([cmd])` (blocking — the assistant freezes until the app exits). No substring/fuzzy matching: you must say exactly "calculator".
- Clever mechanism: nothing new.
- Hidden weaknesses: **Hardcoded Gmail credentials in source** — `sendmail()` does `server.login('example123@gmail.com','Pass@123')`. Everything below the first `main()` call is dead, broken code: it calls `takecommand()`/`speak()`/`sendEmail()` which are never defined, has an `elif` indented under a `try` (syntax error territory), and typos like `'go offlie'`. `subprocess.call` blocks forever on GUI apps. Hardcoded IE path (dead browser). Single-shot: one command per process run.
- Stealable for a stdlib-only Python Windows assistant? **No.** The dict-of-exe-names idea is the tutorial baseline everyone already has; this is its worst form (exact match + blocking call).

## RustamovAkrom/JARVIS (79★, ALIVE — last commit 2026-10-16, PROPRIETARY "All rights reserved", original)
- What it claims / what it is: Multilingual (Russian-first) Windows/macOS/Linux voice assistant. This one has **real substance**: an LLM function-calling agent with a proper plugin/action architecture.
- HOW IT ACTUALLY WORKS (inside): entry → `main.py` (2,540 lines, `JARVIS` class, Gemini Live audio loop, `core/wake_word.py` + `core/hotkey.py`) → Gemini returns a function call → `core/action_loader.py:ActionRegistry.run(name, parameters, ctx)` → handler in `actions/*.py`. Every action file self-declares a module-level `TOOL = {name, description, parameters (Gemini schema), handler}` dict; `action_loader.py:discover_actions()` imports and **validates** every `actions/*.py` at startup (rejects missing name/description/schema/handler) — adding a capability = dropping in one file, zero router edits. Same loader pattern for user plugins (`core/plugin_loader.py:discover_plugins`).
  - Mouse/keyboard: `actions/computer_control.py:computer_control()` dispatch table over `pyautogui` (`FAILSAFE=True`, `PAUSE=0.05`): `_type/_click/_hotkey/_press/_scroll/_drag`. `_smart_type()` clears the field (Ctrl+A, Delete) then, for text >20 chars, pastes via `pyperclip` + Ctrl+V instead of typing char-by-char — much faster and layout-proof.
  - Vision grounding: `computer_control.py:_screen_find()` screenshots with `pyautogui`, sends PNG to Gemini (`core/gemini.py:gemini.call`, FAST tier), prompt demands "ONLY x,y", regex-parses `(\d+)\s*,\s*(\d+)` → `screen_click` clicks it. No UIA/accessibility tree — pure vision coordinates.
  - Window focus on Windows: `_focus_window()` → `subprocess.run(["powershell","-NoProfile","-NonInteractive","-Command", '(New-Object -ComObject WScript.Shell).AppActivate("<title>")'], creationflags=CREATE_NO_WINDOW)`.
  - Volume: `actions/computer_settings.py:volume_up/down/mute()` just press `pyautogui.press("volumeup")` ×5 (media keys); `volume_get()/volume_set()` use **pycaw** (`IAudioEndpointVolume` via comtypes) for real 0–100 values — `volume_get` exists specifically so actions can be **undoable** (`core/undo.py`: record before-value, restore after). Brightness get/set: PowerShell `(Get-WmiObject -Namespace root/WMI -Class WmiMonitorBrightness[Methods])`, Linux fallback `brightnessctl`.
  - App launch: `actions/open_app.py:_launch_windows()` — 3-stage fallback: (1) `shutil.which(name)` → `subprocess.Popen(name, shell=True)`; (2) if name contains ":" → `Popen(f"start {app_name}", shell=True)`; (3) **Start-Menu search automation**: `pyautogui.press("win")`, type the app name, `press("enter")` — works for any installed app with no path knowledge. `_APP_ALIASES` maps friendly names → per-OS binary names, with substring alias matching in `_normalize()`.
  - `actions/desktop.py` also ships an LLM-code executor: Gemini writes Python, run via `exec(compile(...), sandbox)` with a hand-built restricted-builtins sandbox (`_build_sandbox()`, read-only winreg shim, ctypes exposed on Windows).
- Clever mechanism: **the self-describing TOOL-dict + validating auto-discovery registry** (`core/action_loader.py`) — and the undo system keyed on readable before-values (`volume_get` docstring: "a wrong undo is worse than no undo").
- Hidden weaknesses: `open_app` stage 1–2 use `shell=True` with the raw (voice/LLM-supplied) app name — command injection by prompt. `_focus_window` interpolates the window title straight into a PowerShell `-Command` string (quote-break injection). API key read from plaintext `config/api_keys.json`. The `exec` sandbox in `desktop.py` exposes `ctypes` + `getattr` — escapable by construction. `computer_control.py` includes a `random_data` action that **generates fake names/emails/passwords/phone numbers for form-filling** and a `user_data` action that silently falls back to fake data when memory lacks the field — an assistant inventing identity data is a fraud-shaped footgun.
- Stealable for a stdlib-only Python Windows assistant? **Yes — three things:** (1) the Start-Menu-search launch fallback (needs only a key-sender; with stdlib, `ctypes` SendInput or `os.startfile` on a `shell:AppsFolder` search — the *strategy* is stdlib-portable), (2) the TOOL-dict auto-discovery registry pattern (pure Python), (3) media-key volume via `ctypes` `keybd_event(VK_VOLUME_UP)` — the pycaw part is not stdlib, but the media-key trick is.

## AnubhavChaturvedi-GitHub/jarvis-ai-assistant (365★, ALIVE — last commit 2026-08-12, GPL-3.0, TUTORIAL CLONE / kitchen-sink fork)
- What it claims / what it is: A sprawling "JARVIS AI assistant" — recognisably the standard YouTube-tutorial JARVIS lineage (webscout brain, Hinglish command phrases, dozens of single-purpose feature files, committed `__pycache__`, `chromedriver.exe`, chat-history .txt files and a PyWhatKit DB in the repo root).
- HOW IT ACTUALLY WORKS (inside): entry → `jarvis.py` (38 lines) / `co_brain.py` → `Brain/brain.py:Main_Brain(text)` = `webscout.PhindSearch` (a free scraped LLM endpoint — that's the "AI") → `Automation/Automation_Brain.py:Auto_main_brain(text)` — a flat `if/elif` substring chain (`text.startswith("open")`, `"close" in text`, `"play" in text`…) → leaf modules.
  - App open: `Automation/open_App.py:open_App(text)` — tries `subprocess.run(text)` on the **raw utterance remainder**; on exception falls back to the Start-Menu trick: `pyautogui.press("win"); write(text); press("enter")` (with 0.2 s sleeps — flakier than Rustamov's timed version).
  - Volume (the one real Windows API use): `Features/set_get_volume.py` — **pycaw** `AudioUtilities.GetSpeakers()` → `IAudioEndpointVolume.GetMasterVolumeLevelScalar()/SetMasterVolumeLevelScalar(pct/100)`.
  - Brightness: `Features/set_br.py:set_brightness_windows()` — **WMI**: `wmi.WMI(namespace='wmi').WmiMonitorBrightnessMethods()[0].WmiSetBrightness(pct, 0)`.
  - Everything else is pyautogui hotkey wrappers: `Automation/tab_automation.py` (ctrl+t/w, zoom, F11…), `Automation/scrool_system.py` (arrow-key "scrolling", Home/End), `Automation/Battery.py` (psutil), `Features/check_running_app.py`.
- Clever mechanism: nothing new — but note it independently uses the same two real techniques as everyone serious: pycaw for volume, WMI for brightness.
- Hidden weaknesses: `subprocess.run(raw_user_text)` in `open_App` (arbitrary command execution from a voice string is the *primary* path, not a fallback). No error handling in most leaf modules (`except: pass` / bare crashes). Brain depends on `webscout`'s unofficial Phind endpoint — dies whenever Phind changes. GPL-3.0 (copyleft — code can't be lifted into a permissive project). Committed binaries/state files show zero repo hygiene.
- Stealable for a stdlib-only Python Windows assistant? **Partially:** the WMI brightness call is re-implementable stdlib-only via PowerShell `-Command` with `Get-WmiObject -Namespace root/WMI` (no `wmi` package needed) — worth knowing. The rest is the generic tutorial pattern; and GPL-3.0 means steal the *idea*, never the code.

## MAL19INDUSTRIES/JARVIS-OS-V.2 (113★, ALIVE — last commit 2026-08-15, MIT, ORIGINAL — but a sibling fork of the Rustamov codebase, plus an agent layer)
- What it claims / what it is: "JARVIS OS" automation/productivity platform (PyInstaller specs, Docker, FastAPI-ish `api/`, multi-tenant `core/tenant.py`, QA-audit modules). The `actions/` layer is **near-verbatim the Rustamov action set** (same `computer_control.py` structure incl. `_safe_screenshot_path`, `_smart_type`, `_random_data`; same `open_app.py`, `desktop.py`, `computer_settings.py`) — same lineage, rebranded and extended. The genuinely new layer is `agent/`.
- HOW IT ACTUALLY WORKS (inside): entry → `main.py` (2,145 lines) → for multi-step goals: `agent/planner.py:create_plan(goal, context)` — Gemini is prompted with a full tool catalogue and returns a JSON plan of steps (`_fallback_plan()` if the LLM call fails) → `agent/executor.py:AgentExecutor.execute()` runs steps via `_call_tool()` → same TOOL-dict handlers as Rustamov; on step failure `planner.py:replan(goal, completed_steps, failed_step, error)` asks Gemini for a revised plan. Executor also has goal-hygiene hacks: `_ensure_required_save_step()` appends a save step if the goal implies a file, `_inject_context()` threads prior step results into later step parameters.
  - The escalation path is the headline: `agent/executor.py:_run_generated_code(description)` — when no tool fits, Gemini 2.5 Flash **writes a Python program**, it's saved to a temp file and executed with `subprocess.run([sys.executable, tmp_path], timeout=120, cwd=home)` — with a system prompt that literally instructs the model to "Install missing packages with subprocess + pip if needed." Windows Desktop path is resolved properly via `winreg` Shell Folders when `~/Desktop` doesn't exist.
  - Desktop control primitives are inherited: pyautogui dispatch in `actions/computer_control.py`, Start-Menu/`start` launching in `actions/open_app.py` (`Popen(f"start {app_name}", shell=True)`), volume/brightness in `actions/computer_settings.py` (several `shell=True` calls), and `actions/desktop.py:_execute_generated_code()` — a second, in-process code path: `exec(compile(code, "<jarvis_desktop>", "exec"), sandbox)` guarded only by an LLM "UNSAFE" self-check string and a restricted-builtins sandbox that still exposes `pyautogui`, `ctypes` and `os.path`.
- Clever mechanism: **plan → execute → replan-on-failure loop** (`agent/planner.py` + `agent/executor.py`) — the only repo of the seven besides #7 with a real multi-step agent loop and failure recovery, rather than one-shot command dispatch.
- Hidden weaknesses: `_run_generated_code` is **unattended arbitrary code execution of LLM output** (plus self-pip-install) — the single most dangerous pattern in all seven repos; a prompt injection becomes full RCE with the user's privileges. Two parallel code-exec paths (subprocess temp file + in-process `exec`) double the surface. `shell=True` with interpolated app names inherited from the sibling codebase. Sheer sprawl (alembic, multi-tenancy, QA modes) suggests generated/vibe-coded bulk — much of it untested surface.
- Stealable for a stdlib-only Python Windows assistant? **Yes — the planner/executor shape:** a JSON step-plan with per-step results threading + replan-on-error is pure-Python architecture, no deps. Do NOT steal `_run_generated_code` as-is; if ever used, it needs a human gate. (MIT, so the planner code itself is legally liftable.)

## Avinashb722/jarvis-ai-assistant (133★, ALIVE — last commit 2026-07-21, MIT, TUTORIAL-DERIVED kitchen sink, heavily extended)
- What it claims / what it is: Voice + face-recognition JARVIS with "dual AI" (Gemini + local), phone control, emotion detection, proactive mode — ~100 top-level scripts/JSON state files. Built on the classic tutorial skeleton (`engine/command.py:allCommands()` if/elif chain) then expanded far beyond it, mostly sideways into phone automation.
- HOW IT ACTUALLY WORKS (inside): entry → `main.py` (832 lines, eel-style web UI in `www/`) → `engine/command.py:allCommands()` → `process_single_command()` — a giant ordered `elif` substring chain → `engine/features.py` handlers.
  - **Desktop app launch — the one step above tutorial grade:** `features.py:openCommand(query)` looks the name up in a **SQLite DB** (`jarvis.db`, tables `sys_command(name, path)`, `web_command(name, url)`, created in `engine/db.py`) → `os.startfile(path)` for apps, `webbrowser.open(url)` for sites. User-extensible via `add_apps.py` — no code edit to add an app. Fallbacks, in order: hardcoded Android package dict → **ADB control of a tethered phone** (`subprocess.run(f'adb shell monkey -p {pkg} 1', shell=True)`, `adb shell pm list packages | findstr <name>`) → last resort `os.system('start ' + app_name)`.
  - Beyond that, desktop control is thin: no pycaw/WMI volume or brightness module of its own; the bulk of `features.py` (934 lines) is WhatsApp/call/SMS automation — deep links (`start "" "whatsapp:"`, `https://wa.me/…`) + blind `pyautogui.press('enter')`/tab-walking/clicks at fixed coordinates (`input tap 1200 100` on the phone), and `C:\platform-tools\adb.exe` hardcoded paths for dialling/SMS.
  - **Face-rec stack (brief):** textbook OpenCV LBPH — `engine/auth/sample.py` captures 250 Haar-cascade samples at 4 head poses → `trainer.py:train_face_model()` trains `cv2.face.LBPHFaceRecognizer` → `recoganize.py:AuthenticateFace()` gates startup; plus `engine/auth/fingerprint_auth.py`. LBPH + Haar is 2015-era: no liveness, fooled by a photo.
- Clever mechanism: the **SQLite app-path registry + `os.startfile`** — the cleanest app-launch design in repos 1–6 (declarative, user-editable, no shell). The ADB phone-as-second-screen control is unusual, if fragile.
- Hidden weaknesses: `os.system('start ' + app_name)` and f-string `shell=True` ADB commands throughout (voice-text → shell injection). Hardcoded `C:\platform-tools\adb.exe`. Repo root contains committed secrets-adjacent state: `passwords.json`, `password_key.key`, multiple `.db` files with personal data, `battery_report.html`. Fixed-coordinate clicks break on any resolution change. Hundreds of lines of duplicated SMS functions (`sendSMSImproved` repeats the same block 3×). Emotion "AI" in `command.py` is threshold heuristics on brightness/contrast/zero-crossing-rate dressed as analysis.
- Stealable for a stdlib-only Python Windows assistant? **Yes — the app registry:** `sqlite3` (stdlib) `name → path` table + `os.startfile` (stdlib) is exactly the right stdlib-only launcher, better than hardcoded dicts or shell `start`. Face rec: no (needs OpenCV, and LBPH is obsolete).

## ehteshambuildagents/jarvis (23★, ALIVE — last commit 2026-09-25, MIT, ORIGINAL — different species entirely)
- What it claims / what it is: "Holographic UI" JARVIS — and uniquely, the claim is honest about the architecture: package.json describes it as *"a browser voice assistant with an Iron Man holographic interface, driven by Claude Code through a small Node bridge."* No Python, no pyautogui, no hand-written control code at all.
- HOW IT ACTUALLY WORKS (inside): entry → `jarvis.ps1` / `start-jarvis.cmd` launcher (starts the Node bridge hidden, waits for `localhost:5173`, opens Chrome in a real — but off-screen — window because "headless has no audio devices") → React/Vite UI (`src/`) ⇄ WebSocket (`src/lib/bridge.ts`, `ws://localhost:8787`) ⇄ `bridge/server.mjs` (1,518 lines) → **the brain and the hands are the same thing: `@anthropic-ai/claude-agent-sdk` `query()`** — i.e. an embedded Claude Code session (default model `claude-opus-5`, effort `high`). Desktop/browser control is whatever Claude Code's own tools + configured MCP servers do: built-in `Bash`/`Write`/`Edit` for the machine, `chrome_*` MCP tools / chrome-devtools MCP for the user's signed-in Chrome (`bridge/chrome.mjs`, 819 lines of tool-shaping prompts), `bridge/page.mjs`/`vision.mjs`/`panels.mjs` for reading pages, screenshots and HUD panels. There is **zero first-party Windows automation code** — no app-launch table, no volume code; if it opens an app, Claude did it via shell.
  - The holographic UI is **real 3D, not CSS**: `src/scene/Scene.tsx` — react-three-fiber `<Canvas>` with `Core.tsx` (shader-displaced reactor sphere), `Orbits.tsx`, `Particles.tsx`, postprocessing Bloom/ChromaticAberration/Vignette. It's driven by a zustand store (`src/store.ts`) whose `phase` enum (offline/boot/dormant/waking/listening/thinking/tooling/speaking) sets ring spin speed, surface amplitude and accent colour per phase — the reactor literally spins harder while tooling. Voice: Porcupine wake word (web), browser STT by default or ElevenLabs Scribe via the bridge, Kokoro TTS (`kokoro-js`) or ElevenLabs; MediaPipe hand tracking (`src/lib/hands.ts`, 953 lines) and clap detection (`clap.ts`) as extra input channels.
  - The safety layer is the real engineering: `bridge/server.mjs` classifies **every tool call at the bridge boundary** — `READ_ONLY_BUILTINS` set (Read/Glob/Grep/WebSearch… incl. both old and renamed tool names), MCP tools judged by verb regexes (`READ_VERB` vs `EFFECTFUL_VERB` anchored on the tool name, per-server exemptions that can't leak across servers). Reads run free; **anything that writes, shells out, or changes the world is refused unless the bridge was started with `JARVIS_ALLOW_WRITES=1`** (`bridge:writes` npm script) — because, per the code comment, "voice is a bad interface for a confirmation dialog… so the bridge decides." Localhost socket is origin-checked so a random web page can't drive the agent.
- Clever mechanism: **the tool-boundary permission classifier** (name/verb-based, fail-closed to the write branch) + delegating all control to a frontier agent instead of writing 50 brittle pyautogui scripts.
- Hidden weaknesses: Control quality = prompt quality; no deterministic app-launch path (Claude improvises shell commands — slow, token-expensive, non-reproducible). Requires a Claude subscription/API + Node + Chrome; the "assistant" is a thin shell over a paid agent SDK. `JARVIS_ALLOW_WRITES=1` is an all-or-nothing switch — once on, voice commands can reach `Bash` with only the model's judgement as the gate. Default voice ID and secrets handling live in a plaintext `jarvis-secrets.cmd` parsed by the launcher.
- Stealable for a stdlib-only Python Windows assistant? **Not the code** (TypeScript/Node/Three.js, and the control layer is a proprietary agent SDK). **Steal the design law:** classify tools read vs write *at the dispatch boundary*, default-deny writes behind one explicit switch, and never ask for confirmation over voice — decide by policy, not by dialog. That policy pattern is pure architecture and ports to any Python dispatcher for free.

## Cross-cutting verdict
- Real Windows APIs appear in exactly two places across 1–6: **pycaw** (volume) and **WMI** (brightness) — everything else is pyautogui key-presses, media keys, Start-Menu search typing, or shell `start`.
- The Start-Menu-search launch trick (press Win, type name, Enter) appears independently in Rustamov, MAL19 and Anubhav — it's the de-facto "no path knowledge" launcher.
- Most dangerous pattern, twice: LLM-written code executed unattended (MAL19 `_run_generated_code`; in-process `exec` sandboxes in both Rustamov-lineage `desktop.py` files).
- Best architectures: Rustamov/MAL19's self-describing TOOL registry (LLM routing) and ehtesham's policy-gated agent bridge. Best simple mechanism: Avinash's SQLite app registry + `os.startfile`.
