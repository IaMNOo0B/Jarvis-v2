## techgniouss/pdagent — PDAgent / Pocket Desk Agent (15*, ALIVE — last commit 2026-10-19, MIT)
- What it claims / what it is: Self-hosted Telegram bot giving full remote control of a Windows PC, with optional Gemini agentic computer-use. The claim is real — this is the most complete Telegram→PC implementation of the six.
- HOW IT ACTUALLY WORKS (inside):
  - Entry: `pocket_desk_agent/main.py:main()` — PID-file single-instance lock (`acquire_lock()`, verifies the PID is really a bot process via `process_utils:is_bot_process`), builds a `python-telegram-bot` `Application` with a `MarkdownFallbackBot`, `wakepy.keep.running()` to block OS sleep, then `application.run_polling(drop_pending_updates=True)` — outbound long-poll only, no inbound port.
  - Registration/parse: every `/command` comes from one table, `command_map.py:COMMAND_REGISTRY` (~110 commands), and every handler — commands, callbacks, plain messages, photos — is wrapped at registration in `handlers/_shared.py:safe_command`. That decorator is the entire security spine: (1) fail-closed auth `auth.py:is_user_allowed` against `AUTHORIZED_USER_IDS` (update with no identifiable sender is dropped), (2) private-chat-only unless `ALLOW_GROUP_CHATS=true` (so screenshots/clipboard/remote links can't leak into a group), (3) per-user token-bucket `rate_limiter.py:RateLimiter`, (4) catch-all exception → sanitized Telegram error, bot never crashes.
  - Plain text (non-command) → `handlers/core.py:handle_message` → `ai_router.py:AIRouter.send_message` → tries providers in `Config.AI_PROVIDER_ORDER` (Gemini, then NVIDIA NIM), falling to the next only when `ProviderResult.is_retryable_error`.
  - LLM loop: `gemini_client.py:GeminiClient.send_message` — `max_turns = 10`; each turn `_request_with_model_fallbacks()` (ordered model candidates from `_candidate_model_names()`, plus per-mode endpoint fallbacks for the unofficial Code Assist / Antigravity backends) → function calls are funnelled through `ai_tool_loop.py:run_tool_turn`: `normalize_tool_call()` first (a large alias map repairs hallucinated names — `click`/`launch_app`/`remote` → canonical names, aliased arg keys coerced, scroll direction inferred), then a strict `ALLOWED_TOOLS` frozenset check (unknown tool = error returned to the model, logged as "possible prompt injection"), then dispatch.
  - Dispatch: `gemini_actions.py:dispatch_gemini_tool` is two-tier. **Immediate** (read-only): `list_directory/read_file` via `file_manager.py:FileManager`, `capture_screenshot`, `list_open_windows`, `focus_window`, `view_clipboard`, `get_battery_status`, OCR find/click-by-text. **Confirmation-gated** (anything that mutates): `write_file/delete_file/set_clipboard/press_hotkey/click_coordinates/smart_click_text/open_*_app/shutdown_computer/sleep_computer/run_saved_command/update_bot/...` → `_queue_confirmation()` stores a `PendingGeminiAction` (10-char uuid, expiry purge) and sends Telegram Approve/Cancel inline buttons; the callback (`handle_gemini_confirmation_callback`) runs `_execute_confirmed_action()`. Per-tool rate limits sit on top (`_GEMINI_TOOL_RATE_LIMITER`, e.g. screenshot 5/min, clicks 15/min).
  - OS calls: `automation_utils.py:write_text/send_hotkey/press_key` over pyautogui (typing falls back to clipboard-paste + Ctrl+V for characters pyautogui can't type); `gemini_actions.py:_capture_screenshot/_direct_mouse_action` → `pyautogui.screenshot()/click()/scroll()`; OCR in `automation_utils.py:find_text_in_image` (Tesseract) with scored matches; windows via pywinauto (lazy-imported); `file_manager.py:_is_safe_path` = `Path.resolve()` + `relative_to()` against `APPROVED_DIRECTORIES` plus a protected-dirs blocklist (no string-prefix checks); `handlers/system.py:perform_system_shutdown` → `subprocess.run(["shutdown","/s","/t","5"])`, sleep → `rundll32.exe powrprof.dll,SetSuspendState`; app launch resolved through `app_catalog.py` (win32com `Get-StartApps` catalog) instead of raw paths; macros are typed `command_registry.py:CommandAction` sequences (hotkey/clipboard/findtext/smartclick/pasteenter) persisted as JSON and replayed — no shell anywhere in the replay path.
  - Scheduler: `main.py:scheduler_loop` polls `scheduler_registry.py` every 5 s; tasks persist to disk across restarts.
  - Remote desktop: `remote/session.py` mints `secrets.token_urlsafe(32)`; `remote/web_server.py` (aiohttp) serves an MJPEG/WebSocket viewer behind token + `pdremote` cookie + browser-fingerprint check (constant-time compare); `remote/tunnel.py` exposes it via a cloudflared tunnel (auto-installed with winget); `remote/input_bridge.py` injects the viewer's mouse/keyboard.
  - Control stack: Python 3.11+, python-telegram-bot (async), Gemini (API key / Gemini-CLI OAuth / Antigravity OAuth) + NVIDIA NIM fallback, pyautogui/pywinauto/Tesseract/OpenCV, aiohttp + cloudflared for remote desktop.
- Clever mechanism: three, all steal-worthy. (1) **Tool-name alias normalization** in `ai_tool_loop.py` — the model is allowed to hallucinate the tool's name and argument keys; a deterministic normalizer canonicalizes before the allowlist, which is what makes a 10-turn tool loop reliable in practice. (2) **Missed-task grace** in `main.py:missed_task_lateness` — a one-shot task overdue by >600 s (or a scheduled shutdown by >120 s) is *skipped and reported*, never run late: a shutdown scheduled for last night must not fire when the PC boots at 09:00. (3) **Empty-reply history rollback** (`ai_tool_loop.py:finish_empty_reply` + the comment in `run_tool_turn`): a tool exception is reported to the model instead of aborting the turn, specifically so a provider fallback can't re-run earlier tools that already had side effects; an empty model reply is never written into history because one empty part makes Gemini reject every later request.
- Hidden weaknesses found in code:
  - The confirmation gate has a hole by design: `click_on_screen` **with OCR text**, `double_click/right_click/scroll`, `capture_screenshot`, `focus_window` execute *immediately, ungated*. A prompt-injected Gemini turn can click any visible on-screen text (e.g. a "Confirm"/"Allow" button in another app) without the user ever seeing an approval prompt. Only coordinate clicks and `smart_click_text` are gated — the text-click path is not.
  - `automation_utils.py` deliberately sets `pyautogui.FAILSAFE = False` during write/hotkey operations — the move-mouse-to-corner emergency abort is disabled exactly while the bot is typing/clicking.
  - The remote-desktop URL token is the *entire* authentication: anyone who obtains the link gets full mouse + keyboard. `/healthz` in `remote/web_server.py` is unauthenticated, and if the cookie token matches, the browser fingerprint is silently re-bound (fingerprint check only bites when the cookie is absent).
  - Default Gemini path runs against Google's unofficial Code Assist / Antigravity internal endpoints (`gemini_client.py:_get_code_assist_endpoints`, OAuth token files on disk) — functional but ToS-fragile; an auth error auto-logs the user out mid-conversation.
  - `update_bot` tool + `updater.py`: the bot can pip-upgrade itself from PyPI and restart, gated only by the same Telegram approval — PyPI account compromise = PC compromise.
- Stealable for a stdlib-only Python Windows assistant? **YES — the highest-value steal of this group.** `safe_command` (one decorator = auth + rate-limit + crash-proofing), the allowlist + alias-normalization layer, the immediate-vs-confirmation-gated dispatch split, `FileManager`'s resolve/`relative_to` sandbox, and the missed-task grace rule are all pure logic: Telegram long-polling is doable with `urllib`, and pyautogui's role maps onto `ctypes` SendInput. No framework required.

## mpieniak01/Rider-Pc (11*, ALIVE — last commit 2026-10-13, MIT)
- What it claims / what it is: Briefed as a "FastAPI control server on PC" — in reality it does **not** remote-control a desktop PC. It is the PC-side operator console / AI-offload companion for a separate Raspberry-Pi robot (Rider-Pi): the FastAPI server runs on the PC, serves the robot's web UI, and proxies motion/safety commands to the Pi, which is the sole motion executor.
- HOW IT ACTUALLY WORKS (inside):
  - Entry: `pc_client/main.py:main()` — loads `.env`, `Settings()` (`pc_client/config/settings.py`), `CacheManager` (SQLite), `api/server.py:create_app()`, then `uvicorn.run(host=settings.server_host, port=settings.server_port)` with `SERVER_HOST` defaulting to **`0.0.0.0`**, port 8000.
  - App construction: `api/server.py:create_app` registers 11 routers (status, provider, control, voice, chat, project, model, knowledge, home, assistant, mcp), `CORSMiddleware(allow_origins=["*"], allow_credentials=True, allow_methods=["*"], allow_headers=["*"])`, a `ContractMiddleware`, static web UI, and a large amount of in-memory state — including hard-coded placeholder services, a 2×2 placeholder PNG as "last camera frame", and a mock Google-Home state (`authenticated: True, mock-user@rider.ai`) that is only replaced when `test_mode` is off.
  - Command dispatch (the interesting path): `api/routers/control_router.py:api_control_endpoint` — `POST /api/control` accepts only `{move, turn, spin, height, balance, stabilization, action, stop}`; any non-`stop` command must carry a fresh **operator envelope** validated by `core/remote_safety.py:RemoteSafety.command_context`: `generation`, monotonic `seq`, `ts`, `ttl_ms` ∈ [1, 500], and `source == "manual"`, else `409 explicit_fresh_operator_envelope_required`. Then `_proxy_action()` → `adapters/rest_adapter.py:RestAdapter.post_control` → httpx POST to `http://{RIDER_PI_HOST}:{RIDER_PI_PORT}/api/control`. The PC executes no motion itself.
  - Contract gate: `rest_adapter.py:_json_request_once` — before any non-GET (except safety `stop`/`disarm`/`estop`, which deliberately bypass it) it re-fetches `/api/logic/catalog` if the contract check is >10 s old and refuses with `unsupported_contract` unless the Pi speaks the `rider.http` contract. Read paths use single-flight de-duplication (`_read_flights`) and `api/telemetry_snapshot.py` marks every proxied snapshot `stale`/`offline` on failure; a control snapshot whose `safety.contract_version != 1` is forcibly downgraded to `state=UNKNOWN, can_move=False, read_only=True`.
  - Local execution (the only place the PC itself acts): `POST /svc/{unit}` → `core/service_manager.py:ServiceManager.control_service` → `adapters/systemd_adapter.py:SystemdAdapter.manage_service` via `asyncio.create_subprocess_exec("systemctl", ...)` (optionally sudo-prefixed). Guarded: host must be specified for local units, automatic restart of actuating services is forbidden, and starting a unit not in `non_actuating_services` returns `unknown_actuation_capability`. Remote (Pi) services go back through the REST adapter with the same freshness checks (catalog ≤3 s old, `contract_version == 2`).
  - Telemetry/events: `adapters/zmq_subscriber.py` (ZMQ SUB from the Pi), a task queue + provider workers for vision/voice offload (`api/lifecycle.py:ensure_task_queue`, Whisper/Piper/YOLO/Ollama providers), and SSE at `GET /events` (`control_router.py:events` + `api/sse_manager.py`).
  - Control stack: Python, FastAPI + uvicorn, httpx, ZeroMQ, SQLite cache; systemd on the PC side; the actual robot stack lives in the separate Rider-Pi repo.
- Clever mechanism: the **freshness discipline**. Commands are worthless unless fresh (TTL ≤500 ms envelope, sequence + generation), observations are worthless unless fresh (feature toggles require a capability catalog observed ≤3 s ago with the right contract version), and every failure mode degrades toward *read-only / cannot-move* rather than toward permissive. Safety asymmetry is explicit in code: `stop`/`estop`/`disarm` skip the contract pre-flight that blocks everything else.
- Hidden weaknesses found in code:
  - **No authentication at all.** A full grep of `pc_client/` finds no API key, Bearer check, or auth dependency for its own API (only provider keys for LLMs/Google). Combined with `0.0.0.0` binding and `CORS *` + credentials, anyone on the LAN can `POST /api/control`, `POST /api/safety` (`arm` needs only `operator_consent: true` plus any non-empty `operator_plan` string), and start/stop systemd services via `/svc/{unit}`. The operator envelope is **not** a credential — `generation`/`seq`/`ts` are all client-chosen; the code's own comment admits "Pi's sole executor validates…" i.e. this server adds no proof of who is asking.
  - `adapters/rest_adapter.py:RestAdapter.__init__`: `secure_mode` (mTLS to the Pi) defaults off, and if certs are missing it logs a warning and **silently falls back to plain HTTP** — a misconfiguration downgrade with no hard failure.
  - Mock/demo state is baked into the production app object (fake services list, fake camera holder `pid 4242`, mock home devices); `MockRestAdapter` can report motion as executed in demo mode. Fine for a hobby robot, dangerous pattern to copy blindly.
- Stealable for a stdlib-only Python Windows assistant? **PARTLY — steal the protocol idea, not the code.** The expiring command envelope (generation + seq + timestamp + ≤500 ms TTL, replayed/stale commands refused) and the fail-closed stale-snapshot downgrade are excellent patterns for any phone→PC control channel and are trivially implementable in stdlib Python. FastAPI/systemd/ZMQ themselves don't transfer to a Windows stdlib build.

## mylo-2001/hyperclaw (12*, DORMANT — last commit 2026-03-12, MIT)
- What it claims / what it is: An OpenClaw-style personal AI gateway: one gateway process on your PC, agents with real PC tools, controlled from Telegram/Discord/WhatsApp etc. In substance it is a TypeScript re-implementation/fork of OpenClaw (the `LICENSE` even retains "Copyright (c) 2025 Peter Steinberger"; structure, pairing, gateway protocol and tool names mirror OpenClaw throughout).
- HOW IT ACTUALLY WORKS (inside):
  - Entry: `packages/gateway/src/server.ts:GatewayServer` (re-exported by `src/gateway/server.ts:startGateway` with deps from `src/gateway/deps-provider.ts`) — a hand-rolled Node `http` + WebSocket server, default bind `127.0.0.1`, port 18789 (`packages/gateway/src/manager.ts` defaults). Routes include `POST /api/chat`, `POST /api/webhook/inbound`, canvas/state endpoints, channel webhooks, and a web-terminal endpoint that `spawn()`s a shell.
  - Gateway auth: `server.ts` `checkAuth` — Bearer token compared to the configured gateway token, **but `if (!token && !auth) return true`**: with no gateway token configured, requests with no credentials are allowed. WebSocket sessions are created `authenticated: !authToken` — no token configured = every socket is pre-authenticated.
  - Chat → agent: `POST /api/chat` / WS `chat:message` → `callAgent()` → `packages/core/src/agent/engine.ts:runAgentEngine` → `resolveTools()` assembles the tool set (sessions, browser, vision, search, sub-agents, skills, MCP) filtered by `src/infra/tool-policy.ts` (profile/allow/deny) and wrapped by `src/infra/destructive-gate.ts:applyDestructiveGate`. `src/agent/orchestrator.ts:runMultiStep` optionally plans 1–4 steps with an LLM, executes each with up to 2 retries, and checkpoints after each step.
  - **Local execution — this is where the PC is actually controlled**: `packages/core/src/agent/pc-access.ts:getPCAccessTools` (only when `pcAccess=true` in config). Its `run_shell` handler is `child_process.exec(cmd, {cwd: homedir, timeout: 30s, maxBuffer: 10MB})` on the raw model-supplied string — full shell. Sibling tools `read_file/write_file/edit_file` operate on **any path** (the handler itself does no path restriction), plus process list/kill, open app/URL, screenshot, clipboard. A second, richer exec lives in `packages/core/src/agent/exec-process.ts`: `spawn(shell, args)` with foreground/background sessions (auto-background after 10 s `yieldMs`, 1800 s timeout, `process` tool for poll/log/write/kill). An optional Docker mode runs `run_shell` in `alpine` via `execFile` with the cwd bind-mounted.
  - Telegram control — two separate mechanisms: (1) the channel system (`src/channels/runner.ts`, `registry.ts`) with DM **pairing**: an unknown sender gets an 8-char code (`src/channels/pairing.ts:PairingStore`, alphabet without ambiguous chars, 1 h expiry, max 3 pending/channel, allow-lists persisted as JSON with mode `0600`); the owner approves the code and the sender joins `allowFrom`. (2) A standalone companion bot, `src/bot/hyperclawbot.ts:TelegramHyperClawBot` — its own `getUpdates` long-poll loop over axios; `/status /restart /logs /channels /hook …` are answered locally, and `/agent <msg>` is forwarded to `POST {gatewayUrl}/api/chat` with `Authorization: Bearer <gatewayToken>`.
  - Gateway↔node protocol (the "agents on other devices" story): WebSocket only, and only for **mobile** nodes. A phone connects and sends `node_register {nodeId, platform: ios|android, capabilities, token}` (`server.ts:handleMessage`) → registered in `src/services/nodes-registry.ts:NodeRegistry` with a `send()` closure that emits `{type: "node:command", id, command, params}` and awaits the matching `node:command_response` (30 s timeout). Command types are phone capabilities (`camera_capture`, `location`, `sms_send`, `notify`, …). Desktop "nodes" (`src/commands/node.ts`, `nodes.json`) are **bookkeeping only**: `nodeProbe` does `GET http://{host}:18789/api/status` or an ADB ping — there is no task dispatch to a remote PC anywhere in the code. The agent always executes on the machine running the gateway.
  - Control stack: TypeScript/Node monorepo (pnpm workspaces: gateway, core, acp, rag, memory-lancedb), WebSocket + HTTP gateway, Telegram/Discord/etc. channel connectors, MCP client (`src/gateway/mcp.ts` spawns MCP servers as child processes).
- Clever mechanism: the **destructive gate** (`src/infra/destructive-gate.ts`) — channel-sourced sessions (Telegram/WhatsApp/webhook…) cannot run `delete_file`/`kill_process`/dangerous shell patterns (rm -rf, mkfs, curl|sh, fork bomb…) unless the session is elevated; instead the action is parked and the user must reply "confirm". Its approval prompt first **sanitizes invisible Unicode format characters** to visible `\u{...}` escapes, specifically so a zero-width character can't make a displayed command differ from the executed one. Also genuinely good: the exec background-session model (poll/log/write/kill with per-agent stores) and pairing-code onboarding.
- Hidden weaknesses found in code:
  - `src/bot/hyperclawbot.ts:isAllowed` — **`if (this.config.allowedUsers.length === 0) return true;`** An empty allowlist means *every Telegram user on Earth* can drive the companion bot, including `/agent` into a gateway whose tools include `run_shell`. This is the single worst line in all six repos.
  - Gateway auth is opt-in end-to-end (see above): a no-token install bound beyond localhost — and `src/cli/gateway.ts` has first-class `tailscale serve`/**`funnel`** support, i.e. public internet exposure — exposes `POST /api/chat`, `POST /api/webhook/inbound` (any external service that can POST `{message}` drives the agent) and the web terminal.
  - `pc-access.ts:run_shell` is unsanitized `exec()` of model output: any prompt injection that reaches the agent (a web page it browses, a message it reads) is remote code execution as the user. The destructive gate only covers channel sources and a short pattern list; the CLI/local surface and non-patterned commands pass straight through.
  - `src/commands/node.ts:nodeProbe` interpolates a stored device id into a shell string: `` execAsync(`adb -s ${node.androidDeviceId} shell echo ok`) `` — command injection via a node record.
  - Bot token and gateway token sit in plaintext JSON under `~/.hyperclaw/`; the security audit (`src/security/audit.ts`) checks file permissions after the fact rather than the store encrypting anything.
- Stealable for a stdlib-only Python Windows assistant? **PATTERNS YES, CODE NO** (TypeScript throughout). Worth stealing as designs: pairing-code DM onboarding (8 unambiguous chars, 1 h expiry, capped pending list), the channel-vs-local trust distinction with a confirm-to-proceed gate, invisible-Unicode sanitization of approval prompts, and background exec sessions with poll/log/kill. All four are small and stdlib-implementable.

## talmetis-labs/aizen (120*, ALIVE — last commit 2026-10-19, very active, Apache-2.0)
- What it claims / what it is: A Rust AI coding agent that lives on your PC or a VPS and can be driven remotely from Telegram/Discord. Accurate — it is a full agentic coding CLI (17.5k-line `src/agent/mod.rs` alone) with a self-hosted chat daemon bolted onto the same agent loop, not a desktop-GUI controller: it controls the machine through files + shell, not mouse/keyboard.
- HOW IT ACTUALLY WORKS (inside):
  - Entry: `src/main.rs:main()` (`#[tokio::main]`, clap). Bare invocation → interactive REPL (`run_menu`); `aizen agent "<task>"` → one-shot run; `aizen serve` → the hostbot daemon. `--sandbox` pins the process-wide sandbox mode *before anything can spawn a child* — by construction, nothing the model outputs can reach that flag.
  - Agent loop: `src/agent/mod.rs:run_agent_loop_inner` / `run_agent_loop_body`, entered via `run_agent` / `run_agent_loop` / `run_agent_loop_compacting` / `run_agent_loop_full`. State is a `Vec<Message>` (system + history); each iteration calls the `chat` closure (OpenAI-compatible streaming client, `src/llm/client`), appends tool calls, executes them through the `ToolRegistry`, appends tool results, repeats. Budget: `AgentConfig.max_iters` = 25 by default, with progress-based auto-extension (`auto_extend_to`), a budget nudge as the cap approaches, a one-time context-guard nudge at ~90% of the window ("wrap up now"), and mid-loop compaction in the compacting variant (a summarizer model call compresses older turns in place). The `full` variant adds an optional oracle self-review of the final diff before Done. A failed model call rolls back the just-appended nudge so history never ends on an unanswered system message.
  - Tools: `src/agent/builtin.rs` registry — `file_read/file_edit/file_write/file_move`, `shell_run`, `process` (background pool), `web_search/web_fetch/web_crawl`, headless-browser tools, LSP tools (definition/references/diagnostics/symbol replace), memory tools, skill tools, `checkpoint` (git-snapshot timemachine), `notify`, `telegram_send/telegram_ask`, and deferred tools discoverable via `tool_search`. File-mutating tools are classified by `WorkspaceEffect`; effects that `needs_checkpoint()` get a git checkpoint before they run, which powers native undo.
  - Execution + safety (the layered part): a shell command passes (1) `src/agent/cmd_guard.rs:classify` — a deterministic, offline regex classifier with three outputs that matter: `Blocked` (hard floor: `rm -rf /` incl. long-flag and quote-smuggled spellings, `mkfs`, `dd of=/dev/*`, fork bomb, `curl|sh`, recursive `chmod 777 /`, Windows `format C:`, drive-root `del`/`rd`, PowerShell `Remove-Item -Recurse -Force C:\`), `Caution` (history-rewriting git ops — always prompts, with the reason shown), `Allow` (provably read-only shapes, for the smart tier). The floor applies **even under yolo** — approval bypasses the prompt, never the floor. (2) `src/core/approval.rs:ApprovalMode` — `ask` / `smart` (read-only auto-runs) / `yolo`. (3) `src/sandbox/runner.rs` — OS sandbox under the command (Landlock on Linux, Seatbelt `sandbox-exec` on macOS, restricted execution on Windows), prepared via `runner::prepare_*`, never a bare `Command::new`.
  - Remote control: `src/hostbot/daemon.rs:run_daemon` is platform-generic over `hostbot/platform.rs:Platform`. Telegram (`src/hostbot/platforms/telegram.rs`) is hand-rolled on reqwest — **no teloxide**: `Client::get_updates` long-polls `getUpdates` (30 s), and `backlog_offset()` first fetches `offset=-1` so a restarted daemon **skips the ~24 h backlog** instead of replaying old messages as new tasks. Auth is `TelegramConfig.allowed_chat_ids` (`telegram.rs:is_allowed`); with no owner configured the bot boots in **pairing mode** — the first claimer with the code becomes owner and is persisted into `cli-config.json` (`persist_owner`). Discord is a second platform; `src/channels/notify.rs` (Discord/Slack/generic webhook) is outbound-only POST sinks for the `notify` tool.
  - Daemon dispatch: slash commands are parsed by `daemon.rs:parse_slash` (strips the `/cmd@botname` suffix Telegram adds — a bug they document having shipped) → `handle_command`: `/sh <cmd>` runs a shell command immediately (cmd_guard floor still applies), `/agent <task>` runs the agent autonomously with no per-op ask, `/cd`, `/pwd`, `/approval ask|smart|yolo`, `/model`, `/effort`, `/memory`, `/addbot <name> <token>` (host additional bots from the same daemon, each with its own lane/owner). Any non-command message goes to the full agent loop. Concurrency is `src/hostbot/lane.rs`: one queue + worker per `(route, chat)` (in-order per conversation), a `RootGate` that serializes lanes sharing a workspace root (because the workspace-lease map is process-global and would otherwise treat two lanes as re-entrant and drop mutual exclusion), and a global semaphore (default 4, `AIZEN_SERVE_MAX_CONCURRENT`). Sessions persist per `(route, chat)` under `~/.aizen/hostbot/sessions/`; per-bot cwd/model/approval live in `hostbot/lanes.json`, deliberately *not* the machine config, so one bot's `/model` can't switch the terminal session's model.
  - Approvals over chat: destructive ops send inline ✓/✗ buttons; under `serve` the request registers a `oneshot` in a global pending map that the single poll loop resolves; standalone, the tool self-polls `getUpdates` for its own callback. **Timeout = deny after 300 s** (`APPROVAL_TIMEOUT_SECS`).
  - Staying alive on a VPS: `src/hostbot/service.rs` generates a systemd unit (`Restart=always`, `network-online.target`, `loginctl enable-linger` for user units) via `aizen serve --install`.
  - Control stack: single Rust binary, tokio + reqwest, OpenAI-compatible LLM endpoints, Telegram Bot API / Discord, Landlock/Seatbelt sandboxing, git checkpoints.
- Clever mechanism: the **hard floor under yolo** (`cmd_guard.rs`) — a small, deterministic, model-free blocklist that no approval mode, including full autonomy, can override, with patterns checked against the whole (and a quote-stripped copy of the) command string so chaining/quoting can't smuggle a blocked op past it. Runner-up: `backlog_offset()` — two lines that prevent the classic "bot reboots and re-executes yesterday's messages" disaster, which most Telegram bots (including several in this scan) handle only via `drop_pending_updates`.
- Hidden weaknesses found in code:
  - The remote surface is RCE-by-design and knows it: `/sh` and `/agent` from a phone execute arbitrary shell (subject only to the floor). *All* security therefore rests on the Telegram account + `allowed_chat_ids`; a hijacked Telegram session or a phone left unlocked is a hijacked PC/VPS. `/approval yolo` can be set *from the chat itself*, so the approval tier is not an out-of-band control.
  - `/addbot` accepts a new bot **token pasted into chat** and hosts it from the daemon — tokens transit Telegram and sit in chat history/config; a fleet-management convenience that widens the blast radius of any one bot's compromise.
  - `cmd_guard` is regex by design and bypassable by construction: it blocks the `curl … | sh` *shape*, not the act — e.g. downloading then executing in two steps, `python -c` fetching code, or shell aliases/encodings are outside the floor and rely on the approval layer (which yolo disables).
  - Pairing mode trusts first claim: a daemon started ownerless on a VPS is ownable by whoever reaches the bot with the code first; sessions, lanes and history are plaintext JSON on disk.
  - Enormous single-crate complexity (the agent loop file alone is ~17.5k lines with dozens of interacting subsystems — speculation, workflows, blackboard, design mode): powerful, but the audit surface is the opposite of a small assistant's.
- Stealable for a stdlib-only Python Windows assistant? **PATTERNS YES, CODE NO** (Rust, and far too large). Steal: (1) the cmd_guard idea — a short regex hard-floor for catastrophic commands that *no* autonomy mode overrides, checked on the whole command string; (2) approval tiers ask/smart/yolo with read-only auto-allow; (3) deny-on-timeout (300 s) remote approvals; (4) skip-the-backlog on bot startup; (5) one serialized lane per conversation. Each is a page of Python.

## dmrr35/Open.Jarvis (30*, DORMANT — last commit 2026-05-24, MIT)
- What it claims / what it is: Windows-first open desktop voice assistant ("Open J.A.R.V.I.S 1.0.0"). Substantially real: a wake-word voice loop with a local intent router in front of a Groq LLM that emits JSON actions, executed by a validated dispatcher. Turkish-named internals (`komutlar.py`, `ses_motoru.py`) with English-only command tables.
- HOW IT ACTUALLY WORKS (inside):
  - Entry: `jarvis.py` → `open_jarvis/app/main.py:main()` → `open_jarvis/runtime/jarvis_runtime.py:start_jarvis()`. It greets via TTS, spawns a daemon thread for the wake listener, then the main thread polls a module-global `wake_state.active` flag every 0.2 s; an active session auto-returns to standby after `ACTIVE_TIMEOUT` (60 s).
  - Wake: `runtime/wake_listener.py:listen_for_wake_word` — there is **no wake-word engine**. It transcribes successive 3-second mic chunks with full STT (`audio/speech_backend.py:transcribe_audio`, offline model preferred, cloud recognizer otherwise) and substring-matches the wake word (`audio/wake_word.py:wake_word_detected`). Simple and robust to accents; expensive and privacy-relevant (ambient audio is continuously transcribed, and sent to a cloud recognizer when no offline model is present).
  - Command capture: `runtime/command_listener.py:listen_for_command` — `speech_recognition` `Recognizer.listen(timeout=10, phrase_time_limit=20)`, language hard-coded `en-US`, fixed `energy_threshold` from env.
  - Parse/route: `commands/komutlar.py:process_command` — (1) a preference detector can short-circuit ("call me X" etc.), (2) `commands/local_intent_router.py:route_local_intent` — pure normalized-substring/exact matching over static tables (`APP_ALIASES`, `DIRECT_ACTION_PATTERNS`, `WINDOW_ACTIONS`, `KEY_ACTIONS`, `SPOTIFY_ACTIONS`, website aliases, `play … on spotify`, `remember/note …`, Google-search prefixes). A hit produces an action payload with **zero LLM calls**. (3) Miss → `commands/groq_router.py:analyze_with_groq`: Groq chat with a long system prompt demanding *only* JSON — `{"action", "params", "response"}` or `{"actions": [...]}` for multi-task commands — parsed by `providers/groq.py:extract_action_json`, with a provider cooldown on rate-limit errors (`GROQ_COOLDOWN_SECONDS`). Groq is off unless `JARVIS_ENABLE_GROQ` + key, in which case unmatched commands degrade to local-only.
  - Dispatch: `commands/action_dispatcher.py:execute_action` — `commands/action_schema.py:validate_action_payload` first; multi-action payloads run sequentially with a 0.1 s inter-action delay (`JARVIS_ACTION_SEQUENCE_DELAY`); each action is offered to three domain handlers in order: `commands/domains/runtime_actions.py:handle_runtime_action`, `media_actions.py:handle_media_action` (Spotify), `memory_actions.py:handle_memory_action`; first non-`None` wins.
  - OS calls (`runtime_actions.py`): app launch from a **hard-coded path table** `APPLICATIONS` (e.g. `C:\Program Files\Google\Chrome\Application\chrome.exe`, Office16 `WINWORD.EXE`, `%LOCALAPPDATA%\Discord\Update.exe`) via `runtime/process_runner.py:launch_process` → `subprocess.Popen(assert_process_command_safe(cmd), shell=False)` (`security/command_safety.py` vets the argv); fallback is `Popen([app_name])`. Desktop control is pyautogui: `screenshot()` → saved to `%USERPROFILE%\Pictures` + Explorer select, `typewrite`, `press/hotkey` (incl. `win+d` minimize-all, `win+up`, `alt+f4` close), `click/doubleClick`, `scroll`; clipboard via pyperclip; time/date spoken from `datetime`; battery/RAM/CPU via psutil; web via `webbrowser.open` after `integrations/url_safety.py:normalize_web_url` (http/https only); lock → `rundll32.exe user32.dll,LockWorkStation`; sleep → `rundll32.exe powrprof.dll,SetSuspendState 0,1,0`; shutdown/restart → `shutdown /s|/r /t 5` through `process_runner.py:run_command(..., allow_destructive=True)`.
  - Safety gate: `runtime/runtime_safety.py` — `DESTRUCTIVE_ACTIONS = {shutdown, restart, sleep, lock_screen}` are refused in `handle_runtime_action` unless env `JARVIS_ALLOW_DESTRUCTIVE_ACTIONS` is truthy. Note `requires_confirmation()` / `build_confirmation_prompt()` exist in the same file but **nothing on the execution path calls them** — the confirmation API is dead code.
  - Voice out: `audio/ses_motoru.py:speak` — Microsoft Edge TTS (`en-GB-RyanNeural`, rate −8%, pitch −12 Hz) streamed to MP3 bytes and played through pygame's mixer; `asyncio.run()` per utterance, blocking the command loop while speaking. A separate, cleaner `audio/voice_controller.py:VoiceController` (state machine + injected dependencies + TTS queue) exists but is **not** what `start_jarvis` uses — the runtime runs the older global-flag loop.
  - Control stack: Python, speech_recognition (+ offline STT option), Edge TTS + pygame, Groq (optional), pyautogui/pyperclip/psutil, spotipy for Spotify.
- Clever mechanism: **local-intent-first routing**. The common 80% of commands (open app, time, battery, volume, window control, Spotify transport, notes) never touch an LLM — they're deterministic string tables — so they're instant, free, offline, and can't hallucinate. The LLM is demoted to a JSON-action translator for everything else, and its output is schema-validated before anything executes. This is exactly the right architecture for a small assistant, and the cleanest in this group.
- Hidden weaknesses found in code:
  - The Groq JSON is trusted once schema-valid: any in-schema action — including `mouse_click` at arbitrary LLM-chosen coordinates, `type_text` of arbitrary text, `press_key` combos — executes with **no confirmation**. Combined with the dead `requires_confirmation()`, a mis-heard or manipulated command ("close window" → Alt+F4 on unsaved work) has no human in the loop.
  - The destructive gate is an env var most users will simply turn on to make advertised features (sleep/lock/shutdown by voice) work — at which point voice alone, with no speaker verification of any kind, can shut the machine down. Anyone in earshot is authorized.
  - Hard-coded everything: `en-US` recognition + English match tables (no Hindi/Hinglish path despite the codebase's Turkish roots), Office16/Chrome paths, and launching Discord via its `Update.exe` updater binary. `launch_app`'s fallback `Popen([app_name])` passes the raw alias string through when no path matches.
  - Wake-by-full-STT: continuous transcription burns CPU, and in cloud mode streams room audio to a third-party recognizer indefinitely — the privacy cost is structural, not a bug.
  - `speak()` blocking via `asyncio.run()` per utterance + the 0.2 s flag-poll main loop make the whole assistant single-threaded-serial; slow TTS = deaf assistant.
- Stealable for a stdlib-only Python Windows assistant? **YES — the best architectural fit of the six.** The local-router tables, the `{action, params, response}` JSON contract, schema validation, domain dispatcher, and `shell=False` + argv-vetting process runner are all plain Python patterns that translate 1:1 (pyautogui → `ctypes` SendInput/`keybd_event`, psutil bits → `ctypes`/WMI-free equivalents where needed). Copy the architecture, not the hard-coded tables — and wire the confirmation hook they left dead.

## IRISX-AI/IRIS-AI (218*, ALIVE on paper — last commit 2026-09-24 was "Update README.md", custom "IRIS Neural OS License" — source-available, NOT open source)
- What it claims / what it is: A "voice-first operating layer" (Electron + React/TypeScript) claiming hands-free authority over the desktop, an indexed app launcher, system telemetry, a secure API-key vault, and phone control over ADB. **Focus per brief: desktop automation only. Verdict: the desktop automation does not exist in the shipped code — it is a UI shell over unwired IPC.**
- HOW IT ACTUALLY WORKS (inside):
  - Main process is two files, ~200 lines total. `src/main/index.ts:createWindow()` opens a fullscreen, frameless, transparent `BrowserWindow` (`sandbox: false`) and installs a `desktopCapturer` display-media handler (screen-share source selection). It imports `ipcMain` — and **registers zero handlers**. `registerSystemHandlers` is never imported or called anywhere in `src/`.
  - The only automation-adjacent code, `src/main/lib/system.ts`, is **dead code**: `registerSystemHandlers(ipcMain)` would handle `get-installed-apps` (`fetchInstalledApps`: `child_process.exec` of a fixed PowerShell string `Get-StartApps | Select-Object Name, AppID | ConvertTo-Json` on Windows, `mdfind` on macOS, `ls /usr/share/applications` on Linux), `get-system-stats` (`fetchSystemStats`: `os.cpus()` deltas for CPU, `os.totalmem/freemem` — plus **fabricated** temperature `40 + cpu*0.4 + Math.random()*2` and network tx/rx/latency from `Math.random()`), and `get-drives` (`Get-PSDrive` PowerShell / `df -h`). Because it's never registered, none of it runs.
  - The renderer calls channels that have no main-process counterpart, so every one rejects/fails silently: `src/renderer/src/views/APP.tsx` — app cards `onClick={() => window.electron.ipcRenderer.invoke('open-app', app.name)}` — **there is no `open-app` handler and no app-launching code anywhere in the repo**; clicking an app does nothing. `Settings.tsx` invokes `secure-get-keys` / `secure-save-keys` — there is no vault; the keys the UI claims are "securely encrypted and saved" go nowhere. `views/Phone.tsx` invokes `adb-connect / adb-quick-action / adb-telemetry / adb-screenshot / adb-disconnect` (camera/wake/lock/home quick commands, telemetry, screenshot streaming loop) — no ADB code exists in the main process at all. `src/renderer/src/services/system-info.ts` wraps the three dead `get-*` channels and returns `null`/`[]` on failure, so the dashboard's app index and stats are empty in practice.
  - There is no input automation whatsoever: no robotjs / nut.js / pyautogui / SendInput / AppleScript dependency in `package.json`, no click/type/hotkey code path in `src/main` or the renderer. The single `child_process` use in the entire main process is the fixed-string `exec()` inside the dead `system.ts` (no interpolation, so not injectable — merely unused).
  - Preload (`src/preload/index.ts`) exposes the **full** `ipcRenderer.invoke` (any channel, any args) to the renderer, with `sandbox: false` — currently harmless only because there are no handlers to abuse; the moment anyone wires real handlers, any renderer compromise is arbitrary IPC.
  - Control stack: Electron 30 + React 18 + Vite, electron-store/updater declared, Three.js/framer-motion for the visual shell. The engineering effort visibly went into the animated UI, not the control layer.
- Clever mechanism: nothing new in automation. The one reusable idea present (in the dead code) is enumerating launchable Windows apps — including Store apps — with the one-liner `powershell "Get-StartApps | Select-Object Name, AppID | ConvertTo-Json"`, which is a genuinely better app index than scanning `Program Files` (pdagent's `app_catalog.py` uses the same trick, properly wired).
- Hidden weaknesses found in code:
  - Total claims-vs-code gap for the briefed surface: app launching, key vault, phone/ADB control, and live telemetry are all renderer-only — buttons wired to IPC channels nobody implements. This is the "demo UI shipped as the product" failure mode.
  - Fabricated telemetry: `fetchSystemStats` presents `Math.random()`-derived temperature and network numbers through the same object as real CPU/RAM figures, with no marker distinguishing them.
  - Full-IPC preload + `sandbox: false` is a loaded gun left in the codebase for whoever adds handlers next.
  - The custom license prohibits the reuse that MIT/Apache repos in this scan allow — even the ideas must be re-derived, not copied.
- Stealable for a stdlib-only Python Windows assistant? **NO.** Nothing is implemented to steal, and the license forbids copying regardless. The `Get-StartApps` enumeration one-liner is public PowerShell knowledge and is already used properly by pdagent — take it from there.
